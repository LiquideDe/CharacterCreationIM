# Таланты и игровые эффекты

Этот документ описывает **текущее поведение программы** и служит инструкцией для добавления талантов. Правила самой настольной игры могут быть шире: приложение автоматизирует только те эффекты, для которых написан код.

## Где находятся данные и как проходит талант

| Этап | Реализация |
|------|------------|
| Каталог | Один JSON на талант в [`Assets/StreamingAssets/Таланты/`](../Assets/StreamingAssets/Таланты/). На момент проверки — 100 JSON, 100 разных имён. |
| Загрузка | [`TalentCreator.cs`](../Assets/_project/Scripts/Creators/TalentCreator.cs) читает только JSON непосредственно в этой папке, проверяет синтаксис, разбирает `TalentData` и пропускает пустые или повторяющиеся имена. Основной разбор — Unity `JsonUtility`; Newtonsoft используется, только если он бросил исключение. |
| Выбор и покупка | [`TalentUpgradePresenter.cs`](../Assets/_project/Scripts/Presenters/TalentUpgradePresenter.cs) проверяет условия, повторность и доступность. Обычная покупка стоит 100 опыта, в свободном редактировании — 0. Команда добавляет талант в список персонажа, списывает опыт и поддерживает отмену. |
| Другие источники | Фракция и роль тоже могут выдать талант по имени через `FinderData`; см. `FactionPresenter.cs` и `RolePresenter.cs`. Для роли «Мистик» есть отдельная логика выдачи «Псайкера». |
| Сохранение | `Character.Talents` переносится в `CharacterDto` через `CharacterMapper` и сохраняется `CharacterStorage`. Сохраняется экземпляр `TalentData`, включая его описание. |
| Лист персонажа | [`ThirdPage.cs`](../Assets/_project/Scripts/View/Print/ThirdPage.cs) печатает название и описание. Если в сохранённом экземпляре нет описания, ищет его в каталоге по имени. Числовые поля второй страницы считает [`SecondPage.cs`](../Assets/_project/Scripts/View/Print/SecondPage.cs). |

Имя таланта — ключ связи между JSON, требованиями, наградами фракций/ролей, сохранением и специальным C# кодом. Оно должно совпадать везде, с учётом того, что сравнения в разных местах реализованы по-разному. Имя файла может отличаться от `name` (например, `Смерть ведьме.json` содержит `Смерть ведьме!`), но для удобства лучше их согласовывать.

## Формат JSON

Пример таланта с условием и без автоматического эффекта:

```json
{
  "name": "Акимбо",
  "description": "Вы не страдаете от помехи, когда атакуете двумя единицами стрелкового оружия одновременно.",
  "requirements": [
    {
      "type": "specialization_improvement",
      "specialization": "Пистолеты",
      "amount": 2
    },
    {
      "type": "requirement_talent",
      "talents": ["Амбидекстрия"]
    }
  ]
}
```

Это сокращённый пример по действующему [`Акимбо.json`](../Assets/StreamingAssets/Таланты/Акимбо.json); полное игровое описание остаётся в файле каталога.

| Поле `TalentData` | Значение |
|-------------------|----------|
| `name`, `description` | Название и текст для интерфейса и листа. `name` обязателен. |
| `requirements` | Массив условий; отсутствие или `null` означает отсутствие условий. Все условия должны выполняться одновременно. |
| `isMultiple` | Можно покупать несколько раз. По умолчанию `false`. |
| `maxMultiple` | Максимальное число покупок; `0` означает отсутствие лимита. Учитывается только при `isMultiple: true`. |
| `character_creation_only` | Талант показывается в окне покупки только при создании персонажа. |
| `uniqeText`, `currentMultiple` | Поля существуют в модели, но в проверенной логике покупки и печати не используются. Не рассчитывать на них для эффекта. |

Для нового JSON в Unity обычно нужен соседний `.json.meta` с уникальным GUID. Лучше дать Unity создать его при импорте файла; при ручном создании проверить уникальность GUID.

## Требования

Поля условия определены в `TalentRequirement`, проверка — в `TalentUpgradePresenter.CheckRequirement`, показ текста — в `TalentUpgradeView.ParseRequire`. В строковых ссылках на навыки, специализации, характеристики и таланты нужно использовать существующие игровые имена.

| `type` | Нужные поля | Фактическая проверка |
|--------|-------------|---------------------|
| `specialization_improvement` | `specialization`, `amount` | Уровень специализации не ниже `amount`. |
| `skill_improvement` | `skill`, `amount` | Уровень навыка не ниже `amount`. |
| `attribute_min` | `attribute`, `value` | Уровень характеристики не ниже `value`. |
| `attribute_max` | `attribute`, `value` | Сейчас выполняет **ту же проверку `>=`**, что и `attribute_min`; верхний предел не реализован. |
| `no_improvement` | `skill` | Проверяет отсутствие навыка в списке персонажа, а не его нулевой уровень. |
| `requirement_talent` | `talents` | Все указанные таланты должны быть у персонажа. |
| `development_requirement_talent` | `talents` | При создании персонажа пропускает проверку; при дальнейшем развитии требует все указанные таланты. |
| `exclusive_with` | `talents` | Проверяет отсутствие **только первого** таланта в массиве. |

Неизвестный `type` вызывает исключение. Пустой элемент условия считается выполненным. Для `exclusive_with` нельзя оставлять `talents` пустым: используется индекс `[0]`. Интерфейс показывает не все типы одинаково: для `attribute_max` нет отдельного текста, а `exclusive_with` подписан как несовместимость с навыком, хотя проверяет талант. Эти расхождения нужно учитывать при создании нового условия; при необходимости исправлять и проверку, и отображение.

## Повторные покупки

Обычный талант исчезает из списка после первого получения. При `isMultiple: true` он остаётся до `maxMultiple`; `0` означает без ограничения. Исключение — «Псайкер»: допустимое число экземпляров определяется бонусом Силы воли (`Level / 10`), независимо от `maxMultiple`. При повторной покупке используется объект таланта из каталога; этот механизм не хранит отдельные параметры каждого экземпляра, несмотря на наличие `uniqeText`.

Доступность проверяется при построении списка в интерфейсе; команда покупки сама проверяет только достаточность опыта. Свободное редактирование обходит требования, но фильтр `character_creation_only` и ограничение повторных покупок сохраняются. Выдача таланта фракцией или ролью напрямую добавляет его в список и не вызывает `CheckRequirement`.

## Какие эффекты уже вычисляются

В каталоге **нет универсального поля `modifiers`** и в проверенном коде нет реестра или обработчика модификаторов талантов. Описание в JSON само по себе не меняет характеристики, инвентарь или лист. Сейчас есть следующие адресные связи:

| Талант / источник | Автоматическое действие | Где |
|-------------------|-------------------------|-----|
| «Псайкер» | `Character.IsPsyker` обновляется при изменении списка талантов. Это открывает психическую ветку развития и печать психосил. При покупке/выдаче добавляются бесплатная малая и обычная психосила; покупка предлагает выбрать дисциплину. | `Character.cs`, `SkillUpgradePresenter.cs`, `TalentUpgradePresenter.cs`, `RolePresenter.cs`, `FactionPresenter.cs`, `SecondPage.cs` |
| «Санкционированный псайкер» | Если персонаж — псайкер, порог варпа на второй странице равен `2 × бонус Силы воли`; иначе `1 × бонус Силы воли`. | `SecondPage.FillSimple` |
| Экипировка, **не талант** | Текущий вес складывается из веса предметов; десять предметов с нулевым весом дают единицу веса. Предел веса равен `бонус Силы + бонус Выносливости + bonusWeight` от экипировки с `maxWeight`. При нескольких таких предметах код присваивает последнее положительное значение, а не суммирует их. | `SecondPage.CalculateWeight` и `SecondPage.FillSimple` |

Инициатива, раны, рефлексы, оружейные показатели и предел веса на второй странице сейчас рассчитываются без поправок от талантов. Боевые эффекты вроде «Акимбо» остаются текстом на третьей странице для применения игроком в партии.

## Как добавлять следующий талант

1. Сверить название с каталогом и ссылками в других JSON/данных фракций и ролей. Уточнить требования, описание, повторность и доступность при создании.
2. Выбрать уже поддерживаемые `requirements.type`. Если нужного условия нет, добавить его проверку в `TalentUpgradePresenter` и текст в `TalentUpgradeView`; не подменять его похожим условием с другим смыслом.
3. Создать `Assets/StreamingAssets/Таланты/<имя>.json` и Unity `.meta`. Проверить синтаксис, уникальность `name` и имена всех ссылок.
4. Решить по желаемому поведению: если результат должен измениться **в приложении или печатном листе**, найти точку расчёта и добавить автоматический эффект с учётом получения, сохранения, повторных экземпляров и отмены покупки. Сначала проверить, нельзя ли использовать уже существующую точку расчёта. Если эффект действует только во время партии и ничего не меняет в листе, достаточно описания — C# модификатор не нужен.
5. Проверить в Unity: загрузку каталога, доступность таланта при выполненных и невыполненных условиях, покупку и отмену, сохранение/загрузку, нужное поле печатного листа. Если добавлен новый вычисляемый эффект, проверить его отсутствие без таланта и поведение при нескольких экземплярах.

Перед добавлением нового автоматического эффекта нельзя считать поле `description` исполняемым правилом: существующие эффекты реализованы конкретными проверками в C#. По мере появления таких эффектов обновлять таблицу выше, чтобы документация оставалась источником сведений о реально поддержанных расчётах.
