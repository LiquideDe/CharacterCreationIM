# Архитектура: модульный монолит с чистым игровым ядром

## Обзор

Проект развивается из существующего Unity 6 (C#) приложения для создания персонажа в самостоятельный desktop VTT для игр Imperium Maledictum. На первом этапе это один Unity-клиент: тот же билд работает как клиент игрока и как **listen-server** мастера. В дальнейшем его игровое ядро может запускаться как headless dedicated server без переписывания правил.

Выбран модульный монолит: он сохраняет низкую операционную сложность для небольшой команды и бесплатного распространения, но жёстко отделяет домен, Unity-представление, сеть и внешние сервисы. Внутри игровых модулей соблюдается направление зависимостей Clean Architecture.

## Ключевые решения

- **Платформа MVP:** Windows desktop; Linux/macOS — после стабилизации ядра. Мобильные и WebGL не входят в MVP.
- **Авторитет состояния:** хост-мастер. Клиент отправляет намерение (команду), хост проверяет права и правила, меняет состояние и рассылает подтверждённый снимок/патч. Никаких доверенных изменений состояния с клиента.
- **Сеть:** FishNet с transport Tugboat (на базе LiteNetLib) как Unity-слой синхронизации. Базовые режимы: LAN и прямое подключение к мастеру по IP:port; relay — только поздняя опция. Это бесплатное решение без лимита CCU, допускающее listen-server и dedicated server.
- **Связность через NAT:** signalling + собственный coturn (STUN/TURN) на ВМ в РФ; relay — резервный путь, а не обязательный облачный сервис. Не строить безопасность на UPnP и не требовать его от игроков.
- **Голос:** self-hosted LiveKit SFU + coturn. Голос изолирован от игрового транспорта: падение голоса не останавливает сессию. До готовности LiveKit возможен внешний голосовой канал, но он не является частью MVP игрового ядра.
- **Данные кампании:** кампания распространяется мастером как ZIP-архив с версионируемым manifest JSON, JSON-описаниями карт/токенов/эффектов и бинарными ресурсами. Каждый участник импортирует его локально до сессии; формат должен открываться без Unity и иметь миграции версий.
- **Правила IM:** код предоставляет универсальную движковую основу и поставляемые JSON-данные талантов, психосил и иных правил, уже находящиеся в проекте. Клиент также поддерживает локальный импорт пользовательского content pack. Перед публичным релизом владельцы проекта отдельно подтверждают право на распространение поставляемого rule content.

## Контексты и границы

```text
Unity UI / 2D renderer / Editor tools
                |
         Application use cases
  (MoveToken, ApplyEffect, Attack, ChangeMap)
                |
      Domain: campaign + encounter + rules
                |
 Ports: persistence | networking | media | clock | RNG
                |
 Unity/FishNet adapters | local files | LiveKit | server services
```

### Доменные модули

| Модуль | Ответственность | Не знает о |
|---|---|---|
| `Campaign` | manifest, доступ, сохранения, миграции | Unity, сеть |
| `Map` | карта, слои, полигональные зоны, топология переходов, мастерская видимость | UI, аудио |
| `Encounter` | токены, порядок хода, владельцы, журнал событий | FishNet |
| `Rules` | проверки, атаки, оружие, состояния, бафы/дебафы | MonoBehaviour, файлы |
| `Media` | плейлист, команды управления, версия ресурсов | конкретный сетевой transport |
| `Session` | роли GM/player/spectator, присоединение, reconnect | реализация UI |

Новые игровые модули получают отдельные `.asmdef`; существующий код создания персонажа мигрируется постепенно, только когда понадобится в VTT. Не смешивать новые VTT-классы с `Assets/_project/Scripts` без явного плана миграции.

## Правила зависимостей

- `Domain` — чистый C#, не зависит от Unity, FishNet, Zenject, файловой системы или сетевых DTO.
- `Application` зависит только от `Domain` и портов-интерфейсов.
- `Networking`, `Persistence`, `Media` реализуют порты и могут зависеть от Unity/пакетов.
- `Presentation` вызывает application use cases; она не изменяет сущности напрямую.
- Между модулями — только публичные контракты и события; нельзя обращаться к внутренним классам соседнего модуля.
- `MonoBehaviour` хранит ссылки на представление и адаптеры, но не содержит правила боя.

## Модель синхронизации

```text
Client input -> Command {id, expectedRevision, payload}
             -> Host validates role + current state + rules
             -> Domain event(s) appended to encounter log
             -> authoritative revision increases
             -> StatePatch/Snapshot broadcast to authorised clients
             -> clients render confirmed state
```

- Каждая команда имеет UUID, автора, версию состояния и корреляционный ID: повторы при reconnect не создают второй бросок или атаку.
- Случайность генерирует только хост; в журнал пишутся seed/результат/формула, если это допустимо для мастера.
- Для живого перетаскивания токена допустима локальная визуальная предикция, но итоговую координату подтверждает хост.
- Переподключившийся клиент получает компактный snapshot, затем события после его ревизии.
- Master имеет отдельные GM-команды: скрыть/открыть токен, изменить карту, отредактировать зоны, выдать эффект, откатить допустимое последнее действие.

## Карта и контент

- Координаты карты — нормализованные world units, а не пиксели исходного изображения; изображение хранит свои размеры и content hash.
- Навигационные зоны образуют разбиение карты на полигоны, как районы в Cities: Skylines. Отдельных сущностей стен и дверей нет: совпадающий участок границы двух зон образует вычисляемый `ZoneConnection` — переход между ними.
- Редактор привязывает вершины к заданной сетке/допуску. При публикации карты topology builder сопоставляет коллинеарные граничные сегменты двух зон с одинаковыми координатами в пределах допуска и создаёт переход. Граница без соседней зоны остаётся непроходимым внешним контуром.
- Позже состояние прохода (например, закрыт/заперт) будет прикрепляться к стабильному ключу `ZoneConnection`, а не к отдельному объекту `Door`; вычисление переходов остаётся детерминированным у хоста.
- Активные области — отдельные trigger-полигоны с условиями и безопасными действиями, а не исполняемый пользовательский C#.
- Туман войны MVP — ручная видимость зоны: мастер открывает/скрывает зону для группы `players`; расчёта line of sight или индивидуального поля зрения персонажа пока нет.
- Хост формирует player-snapshot с учётом видимости: скрытые токены, эффекты, активные области и их события не посылаются игроку, а не только прячутся Unity-интерфейсом. Мастер всегда получает полное состояние.
- Карта имеет стабильный `mapId`, `revision`, ссылку на изображение по SHA-256 и authored-by/updated-at метаданные.
- Клиент сверяет хеши ресурсов при входе. Недостающие ресурсы берёт либо из кампании хоста, либо из настроенного object/media storage; состояния игры не должны зависеть от URL файла.

При распространении полной карты ZIP-архивом этот туман является игровой, а не криптографической защитой: изображение уже находится на устройстве игрока, хотя клиент не покажет его под overlay и не получит скрытые игровые объекты. Для жёсткого сокрытия изображения в будущем потребуется раздавать тайлы/кропы только по мере открытия — это отдельная поздняя фича.

## Инфраструктура

### Рекомендуемая минимальная топология

```text
Players -- HTTPS/WSS --> signalling (small VPS, RU region)
   |                         |
   +-- game UDP/TCP --> GM host / optional relay
   +-- WebRTC audio --> LiveKit SFU <--> coturn

GM host -- encrypted backup --> chosen storage
```

1. **MVP без инфраструктуры:** мастер отправляет ZIP кампании участникам любым внешним способом; каждый импортирует её в клиент и видит совпадающий content hash. Игра работает в LAN или игрок вручную вводит публичный IP/имя мастера и порт. Хост при необходимости пробрасывает один игровой порт на роутере. По сети идут только команды, ревизии, броски и snapshots; голос временно вне приложения.
2. **Практический интернет-режим (опционально):** одна небольшая Linux ВМ у российского провайдера (например, Yandex Cloud или другой проверенный локальный VPS) с Docker Compose: signalling, coturn и позднее LiveKit. Она требуется только когда direct connect не проходит через NAT/CGNAT или когда нужен встроенный голос.
3. **Позднее:** S3-совместимое хранилище (Yandex Object Storage или self-hosted MinIO) для удобного распространения больших ресурсов, Postgres только когда появятся аккаунты/общий каталог кампаний. До этого кампании локальные и приватные.

Нельзя обещать, что любой адрес или протокол «никогда не будет заблокирован»: доступность зависит от РКН, региона, DNS и сети игрока. Перед публичным релизом обязателен smoke-test из российских домашних и мобильных сетей; домен, ВМ и резервный провайдер должны быть заменяемыми конфигурацией.

### Безопасность и приватность

- В direct-режиме игрок вручную вводит endpoint и одноразовый invite-код; не показывать публичный список игровых серверов. Вход ограничен паролем/кодом комнаты и лимитом попыток. Invite не заменяет IP, port forwarding или relay: без сервиса signalling он не умеет находить хост за NAT.
- TLS для HTTP/WSS, DTLS/SRTP для WebRTC; TURN с краткоживущими credentials, никаких постоянных паролей в клиенте.
- Лимиты размера файлов, MIME allow-list, проверка хеша, уникальные имена; никаких загружаемых скриптов и архивов, распаковываемых автоматически.
- Логи не содержат invite-коды, TURN secrets, IP-адреса в обычном INFO-режиме, имена локальных файлов или содержимое чата.
- Автосейв на хосте, атомарные записи, ротация минимум трёх резервных копий; восстановление тестируется на копии.

## Наблюдаемость

- Структурированные логи с `sessionId`, `commandId`, `mapId`, `revision` и уровнем DEBUG/INFO/WARN/ERROR.
- DEBUG отключён в релизе по умолчанию; секреты редактируются перед выводом.
- Метрики инфраструктуры: доступность signalling/LiveKit, число комнат/участников, TURN relay traffic, ошибки подключений. Без телеметрии игроков наружу без opt-in.

## Не включать в MVP

- Учётные записи, публичный маркетплейс и облачный каталог кампаний.
- Автоматическое исполнение произвольных модов/скриптов.
- Динамическое освещение, автоматическое индивидуальное поле зрения, видео, мобильные клиенты, браузерная версия.
- Полный цифровой набор правил/артов Imperium Maledictum.

## ADR

Принятые решения записаны в `docs/adr/`. Сетевой sandbox создаётся после базового VTT bootstrap; затем Tugboat проверяется на реальных LAN/Internet соединениях, а параметры таймаутов/порта фиксируются в ADR-004.
