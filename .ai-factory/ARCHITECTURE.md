# Архитектура: слои существующего Unity-приложения

## Обзор

Проект организован по техническим ролям внутри одного Unity-приложения. Экранные компоненты и презентеры показывают данные, медиаторы управляют последовательностью действий, загрузчики читают игровые справочники, а модель персонажа и сериализация хранят состояние. Это описание фиксирует действующую структуру без переноса файлов.

## Основание выбора

- Тип проекта: настольный редактор персонажей на одной основной сцене Unity.
- Стек: C#, Unity 6, Zenject, R3, UniTask, JSON-файлы.
- Существующие каталоги `Creators`, `Mediators`, `Presenters`, `View` и `Installers` уже задают разделение ответственности.

## Структура каталогов

```text
Assets/
  Scenes/GameScene.unity
  _project/
    Scripts/
      Character.cs, CharacterDto.cs, CharacterMapper.cs, CharacterStorage.cs
      Creators/       загрузка и поиск игровых данных
      Factories/      создание компонентов и презентеров
      Installers/     регистрация зависимостей Zenject
      Mediators/      сценарии создания, развития и редактирования
      Presenters/     логика отображения экранов
      View/           MonoBehaviour-компоненты экранов, печать листов
    Prefabs/          интерфейсные префабы
    SO/               ScriptableObject-конфигурация
  StreamingAssets/    игровые справочники и сохранённые персонажи
```

## Зависимости и обмен данными

1. `Bootstrap` получает загрузчики `IDataCreator`, загружает справочники и передаёт управление `StartMediator`.
2. Медиатор запрашивает экран через `PresenterViewFactory`, подписывается на события презентера и передаёт ему модель `Character`.
3. Презентер получает действия из `View`, обновляет состояние и передаёт изменения следующему шагу сценария.
4. `Creators` читают справочники из `Application.streamingAssetsPath`; `CharacterStorage` преобразует состояние через `CharacterMapper` и `CharacterDto` для JSON.
5. `Installers` связывают эти объекты через Zenject; ссылки на `View` и префабы должны соответствовать реальным компонентам Unity.

Поток управления идёт от интерфейса к презентеру и медиатору; игровые данные поступают от загрузчиков к сценарию. Модель и форматы данных не должны зависеть от конкретного префаба. Сохраняйте существующие прямые зависимости там, где они уже нужны, и не добавляйте новые связи с Unity UI в код загрузки или сериализации.

## Принципы для изменений

- При добавлении игрового справочника создавайте загрузчик с проверкой файла и понятным сообщением об ошибке, затем регистрируйте его в Zenject, если он нужен при старте.
- При добавлении экрана согласуйте имя `*View` с `*Presenter`, запись в `ViewPrefab` и переход в медиаторе: `PresenterViewFactory` ищет презентер по имени.
- При добавлении поля персонажа согласуйте `Character`, `CharacterDto`, `CharacterMapper`, сохранение и печатный лист.
- Для долгой загрузки сохраняйте `CancellationToken`; для событий освобождайте подписки при завершении сценария.
- Не считайте наличие JSON и кнопки доказательством готового функционала: проверяйте путь от действия пользователя до сохранения и отображения результата.

## Примеры действующего подхода

Загрузка справочников перед открытием меню (`View/Bootstrap.cs`):

```csharp
var loadTasks = _creators.Select(c => c.LoadAsync(cts.Token)).ToArray();
await UniTask.WhenAll(loadTasks);
_startMediator.ShowMainMenu();
```

Преобразование модели в JSON через отдельный mapper (`CharacterStorage.cs`):

```csharp
public static string ToJson(Character character)
{
    var dto = CharacterMapper.ToDto(character);
    EnsureCollections(dto);
    return JsonConvert.SerializeObject(dto, Settings);
}
```

## Организация существующего кода

Новые функции размещайте в подходящих существующих каталогах. Изменяя старые классы, сохраняйте их действующие контракты с префабами и сериализацией; перенос unrelated кода в новые слои не требуется. Сложные правила, которые начинают разрастаться внутри экранов или медиаторов, выделяйте в отдельные классы в `Scripts` по их назначению.

## Типичные ошибки

- Добавить кнопку и JSON, но оставить пустым её обработчик.
- Изменить поле модели, не обновив DTO и mapper.
- Создать `View` и `Presenter`, не зарегистрировав нужные зависимости или префаб.
- Читать справочник без проверки пути, формата и отмены загрузки.
